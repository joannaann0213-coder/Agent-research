Agent 连接器与 MCP

一个第三方应用，是怎么接进 AI agent 的？这里按提问的顺序拆开讲：底层协议、各家自建的接入层、连接器目录、认证方式、“连接一个应用”背后的授权，以及怎么在自己的 agent 产品上搭一套，把现有的 MCP 迁进来。

2026 年 10 月 23 日 · 11 月 18 日修订，改动见文末修订记录 · 依据 MCP 规范、各家公开文档和报道 · 标有 推断 的是分析判断，不代表任何公司的官方说法 · 团队共享 agent 和工作助理，另见姊妹篇《共享 Agent 与工作助理》

用户看到的

连接一个应用这一步就是一次授权。用户看不到 MCP。

产品要做的

自建一层接入层目录、授权、令牌保管、调用网关，每个 agent 产品做一次。

应用方要做的

做一个 MCP 服务器做一次，所有支持 MCP 的 agent 都能接。

提问路线

下面按提问的先后顺序展开。每个问题先写分析思路，再写结论。

  1. 问题一连接器是什么原理？每个 agent 产品都要逐个适配吗？底层是 MCP。每家自建一次接入层，接标准应用只是填配置；要逐家处理的只剩四件事。
  2. 问题二目录条目里存了什么？和官方 MCP Registry 什么关系？注册表是上游的“黄页”，只存元数据；产品目录再加审核、图标和认证配置。
  3. 问题三常见的图标和接入方式：OAuth、key、用户名密码？大多数走 OAuth；key 留给共用和无人值守；密码只在应用自己的页面上输。
  4. 问题四用户不懂 MCP，连接一个应用到底授权了什么？一次授权，五个开关：能碰什么、谁能用、开哪些工具、动手前问不问、怎么收回。
  5. 问题五在自己的 personal agent 上怎么搭？存量 MCP 怎么迁？七个模块、八张表；存量服务器分四类迁，再统一走三步。
  6. 问题六能把三方 MCP 封装成自己的连接器吗？agent loop 也走 MCP？都对。模型只决定调哪个工具，调用由 harness 经网关发出。
  7. 问题七为什么 Claude Tag 推连接器和插件，没有单推 skill？skill 装进插件，和连接器一起由管理员把关。在共享 agent 里，skill 也是一种权力。

先认识几个词

Agent
能自己调用工具、分几步把一件事做完的 AI，不只是聊天。
连接器
让 agent 接上某个应用的“钥匙”。连接时，你在那个应用自己的页面上登录授权；之后 agent 就按这份授权读写里面的数据。
MCP
连接器的通用规格，全称 Model Context Protocol。应用方按它做一次，所有支持 MCP 的 agent 都能接入。
服务器、客户端
应用方提供 MCP 服务器，对外暴露工具和数据；agent 产品里内置 MCP 客户端，去连这些服务器。
工具
服务器提供的一个个动作，比如“搜索邮件”“创建工单”。每个都带名称、说明和参数格式，模型靠这些决定调哪个。
接入层
每个 agent 产品在后端自建的一层，管目录、授权、令牌和调用。用户看到的“应用”页面，背后就是它。
OAuth
一种标准授权方式：你在应用自己的页面登录，再把有限的权限交给第三方，第三方拿不到你的密码。
令牌
授权完成后，应用发给 agent 产品的通行证。它有范围、会过期、能撤销。
Skill
一份按需读取的说明书，教 agent 某件事该怎么做。它本身不带任何访问权。
插件
把连接器、skill 和常用命令打包成一次安装的套装。

问题一

连接器是怎么接进来的

提问

深入调研一下 agent 里连接器的技术架构原理。第三方系统怎么添加、怎么连接？是不是要 agent 产品逐个适配到自己的配置页面？比如 Claude、Cursor 的 Grok Bot、ChatGPT 里的连接器，感觉每个 agent 产品都要适配一下。

追问

我在想，实现层应该有一个接入的抽象层。我知道底层是 MCP。

分析思路

  1. 读 MCP 规范：谁和谁通信、怎么传输、怎么授权
  2. 对照 Claude、ChatGPT、Cursor、Grok Bot 的接入文档，看“添加应用”背后发生了什么
  3. 把“每家 agent 做一次”的事，和“每个应用都要逐家处理”的事分开

结论

你的直觉是对的：每家 agent 都自建了一层接入层，对外统一走 MCP。接一个标准应用基本只是填配置，不用写代码；还要逐家处理的只剩四件事。

从“两两对接”到“各做一次”

MCP 由 Anthropic 在 2024 年 11 月发起，2025 年 12 月捐给了 Linux 基金会下的 Agentic AI Foundation。它要解决的是对接数量的问题：

MCP 里有什么

部分是什么例子
工具agent 能调用的动作，每个都带名称、说明和参数格式搜索邮件、创建工单
资源agent 能读取的数据一个文件、一条记录
提示服务器预设的提问模板“总结这个 PR”
传输本地服务器用 stdio，在你电脑上作为子进程运行；远程服务器用 Streamable HTTP读本机文件的工具；各家官方的远程服务器
授权远程服务器用 OAuth 2.1跳到应用自己的登录页
扩展按需加的附加能力MCP Apps（工具返回交互界面）、Tasks（长任务）、Skills（随服务器下发说明书）、企业托管授权

最新一版规范在 2026 年 7 月 28 日发布，是 MCP 进入基金会后的第一版。最大的变化是核心改成了无状态：去掉开场握手和会话 ID，每个请求自带协议版本和能力信息；服务器必须提供 server/discover，告诉客户端自己支持什么。请求头里还要带上方法名，网关不用拆开请求体就能路由，负载均衡也不再需要“粘性会话”。Roots、Sampling、Logging 三项被标为弃用，Tasks 挪进了扩展。服务器要向用户追问时，也不再主动发请求，而是返回 input_required，由客户端补齐答复后重发原请求（MRTR）；工具清单这类列表结果，还要带上缓存时长和缓存范围（ttlMs、cacheScope）。

每家 agent 做一次：接入层

你说的“抽象层”就是它。每个 agent 产品在后端自建一层，把所有连接管起来：

  • 目录与上架。管“有哪些应用可以连”，条目只存元数据（见问题二）。
  • 安装与策略。记录谁连了什么、在哪些对话里能用、每个工具是允许、先问还是禁用。
  • 认证代理与凭据库。跑授权流程，加密保管令牌，自动刷新，随时撤销。
  • 工具注册表。把各服务器的工具交给模型，加命名空间（按安装起名，同一应用连两个账号也不撞名）；工具多时按需加载（见问题六）。
  • MCP 网关。和三方服务器通信，管超时、重试（只自动重试只读或幂等的工具）、结果大小和出网白名单。
  • 原生适配器。谷歌、微软这类巨头生态，或者根本没有 MCP 服务器的系统，自己写适配，对上层暴露成同样的工具。

在四家产品里“添加一个应用”

产品用户怎么加背后是什么
Claude从连接器目录里点选；也可以粘贴远程 MCP 服务器地址，添加目录外的连接器远程 MCP，OAuth 或请求头认证；Team 和 Enterprise 要先由管理员把连接器加到工作区
ChatGPT从插件目录里连接；开发者模式（测试版）可以添加自定义 MCP 服务器应用和插件底层都是 MCP；桌面端和 Codex 共用一份 MCP 配置
Cursor点“一键安装”链接，或者在 mcp.json 里写服务器地址或启动命令远程地址，或本地 stdio 进程
Grok Bot在“连接应用”里连插件，同一账号下的 Bot 共用这些连接连上一个插件，就允许 agent 读取、操作或监控那个服务

每个应用还要逐家处理的四件事

  • 客户端身份。你的产品要让每个应用的授权服务器认得自己。跟对方有预注册关系的，先用预注册的 client_id；否则首选 CIMD（客户端身份元数据文档）：在自己的域名上放一份描述文件，它的网址就是 client_id，到哪都能用。两者都不行，才回退到 2026 年 7 月版已标为弃用的动态注册（DCR）。也有应用要求更多，比如 Slack 要求接入方先建一个 Slack 应用。
  • 目录审核。应用方要分别向 Claude、OpenAI 等各家的目录提交，各过一遍审核。
  • 功能差异。各家支持的规范版本和扩展不完全一样。比如交互界面 MCP Apps，今年 1 月成为第一个官方扩展时，只有 Claude、ChatGPT、VS Code 测试版和 Goose 支持。
  • 巨头生态。谷歌、微软的邮件、日历和文档，要自己注册 OAuth 应用、过对方的审核，往往还要做原生对接和同步索引。

问题二

目录条目和官方注册表

提问

连接器目录条目里具体存了哪些元数据？和官方 MCP Registry 是什么关系？

分析思路

  1. 读官方 MCP Registry 的发布说明和 server.json 格式
  2. 读 Claude、OpenAI 的连接器提交和认证文档
  3. 把条目里的字段，按“从哪来”分开

结论

官方 MCP Registry 是上游的“黄页”：只记有哪些服务器、在哪、谁发布的，不存代码，也不做背书。各家产品目录从它同步，或者直接收应用方的提交，再加上审核、图标、权限说明和认证配置。用户看到的是产品目录。

一个目录条目里有什么

类别存什么从哪来
身份名称（反向域名格式，如 io.github.用户名/服务器名）、版本、发布方官方注册表的 server.json；名称前缀在发布时验证过归属
连接远程地址和传输方式；或者本地安装包（npm、PyPI、Docker 等）和启动方式server.json 里的 remotes 和 packages
展示标题、一句话简介（100 字符以内）、图标、官网链接server.json，加上服务器在协议里声明的 icons 和 websiteUrl；产品目录通常再审一遍
认证认证方式（OAuth、请求头、无）、授权服务器、需要的权限范围连接时向服务器发现；你的产品自己的 client_id 由产品保管
能力工具清单：名称、说明、参数格式、只读或破坏性注解连接后从服务器拉取，存成快照
治理审核状态、隐私政策、数据用途、企业里谁能装产品目录自己加

自建目录时，条目可以直接从 server.json 导入。平台私有的字段放在 _meta 下、用自己的命名空间，不和标准字段混在一起。

注册表不是背书

  • 只验证归属。发布时用 GitHub 账号、DNS 记录或网站上的验证文件，证明名称前缀是你的；代码本身不审。
  • 只删明显的坏东西。违法内容、恶意软件、垃圾信息、根本不能用的服务器会被删；质量差、有漏洞、重复的不会。按它自己的说法，进注册表是分发，不是背书。
  • 不给客户端直接读。它的定位是给下游的目录和市场用，由它们决定展示什么、怎么扫描。
  • 还在预览。2025 年 9 月上线，由 Anthropic、GitHub、微软、PulseMCP 等支持，目前不承诺可用性和数据持久性。

问题三

图标和接入方式

提问

在 agent 产品上，一些常用的连接器图标、logo，还有接入方式，比如 token、key，还有用户名密码吧？

分析思路

  1. 看一张连接器卡片上的信息，各自从哪来
  2. 统计常见应用的官方远程服务器用什么认证
  3. 比较几种方式下，长期有效的秘密落在谁手里

结论

绝大多数 SaaS 走 OAuth：用户跳到应用自己的页面登录，产品拿到的是令牌。API key 和 token 用在团队共用或无人值守的场景。用户名密码只该出现在应用自己的登录页，或者数据库这类“自定义连接”里。

一张连接器卡片

图标从哪来

2025 年 11 月那版规范加入了 icons 字段（SEP-973）：服务器本身、每个工具、资源和提示都可以带图标，给出多种尺寸和格式，服务器还能带一个官网链接。规范同时提醒客户端：只从服务器自己的域名或可信域名加载图标；SVG 里可能藏着脚本，要做防护。所以产品目录一般会把审核过的图标存一份，不在用户打开页面时临时去抓。

图标只回答“这是谁”，不代表安全。授权页上真正要写清楚的，是发布方和权限。

几种接入方式

方式用户要做什么产品保管什么适合
OAuth 2.1跳到应用自己的登录和同意页，点“允许”访问令牌和刷新令牌：有范围、会过期、能撤销每人用自己账号的 SaaS，绝大多数连接器
API key、token在应用后台生成一串密钥，粘贴进来这串密钥本身，通常长期有效团队共用、无人值守、内部 API
用户名密码填地址、用户名、密码连接串或密码数据库、自建系统这类自定义连接
企业托管授权用公司账号登录一次，不用逐个点同意公司身份系统换来的令牌公司统一管理的员工应用
无认证什么都不用做无公开数据

OAuth 2.1 删掉了“把密码直接交给第三方”的密码模式。所以正规的连接器里，用户名密码只出现在应用自己的登录页，或者“自定义连接”表单里。

企业托管授权是 MCP 的一个扩展，2026 年 6 月 18 日宣布稳定。员工单点登录时，公司的身份系统签发一份身份断言，产品拿它去应用那边换令牌，员工不会看到逐个应用的同意页。首个支持的身份提供商是 Okta；客户端有 Anthropic 的 Claude 和 Claude Code、微软的 VS Code；服务器有 Asana、Atlassian、Canva、Figma、Granola、Linear、Supabase，Slack 等正在加入。

应用本地版怎么认证官方远程地址远程版怎么认证
GitHub个人访问令牌（PAT），放在环境变量api.githubcopilot.com/mcp/OAuth；也可以把 PAT 放进请求头
Notion内部集成令牌mcp.notion.com/mcpOAuth

Stripe 是一个正在发生的例子：它要求在 2026 年 11 月 30 日前迁完，12 月起它的 MCP 服务器不再接受完整权限的 secret key，也不再接受没有 Agent 标签的受限 key，只认 OAuth 或新建的 agent API key。

团队场景：钥匙用谁的

同一个连接器放进团队共用的 agent，就多了一个问题：用谁的钥匙。Grok Bot 的团队版是这样分的：OAuth 类插件用正在跟它说话的那个人的账号，填 key 的插件用 Bot 自己的共享凭据。Claude Tag 的默认做法不同：频道里用组织开通的服务账号；仓库里的 .mcp.json 不会加载，会话只能经管理员给频道配的连接访问外部服务，密钥在网络层注入，从不进沙箱。姊妹篇专门比较了这几种做法。

问题四

连接一个应用，就是一次授权

提问

我知道底层是 MCP，但普通用户根本不懂 MCP。本质上，我连接一个应用，就是授权了相关的工具和数据。

分析思路

  1. 把一次连接拆成用户看得到的步骤，和后台发生的事
  2. 对照 OAuth 授权码流程和 MCP 的授权规范
  3. 列出连上之后，用户还能控制什么

结论

对。对用户来说没有 MCP，只有“连接一个应用”。这一步本质上是一次授权，背后有五个开关：能碰什么、谁能用、开哪些工具、动手前问不问、怎么收回。

点下“连接”之后

几个容易忽略的细节：令牌要“绑定受众”，发给 A 服务器的令牌不能拿去调 B；凭据按签发它的授权服务器分开存，授权服务器变了就重新注册；回调时要核对授权响应里的签发方（iss），防止被换成别家的授权码。受众绑定从 2025 年 6 月那版规范起就是要求；按授权服务器分开存、核对 iss，是 2026 年 7 月那版新写进去的。

连上之后的五个开关

  • 读写分级靠工具注解。MCP 的工具可以自带提示：只读（readOnlyHint）、会破坏数据（destructiveHint）。默认只读的直接放行，写入先问，破坏性操作每次都问；没有注解的也按“先问”处理。注解是服务器自报的，只能当提示，不能当保证。例外是会访问外部网络的只读工具：对话里已经混入别的应用的数据时，它也能把数据带出去，要按“先问”处理。
  • 应用那边还有一道闸。Stripe 对退款、对外付款这类写操作，要求人到 Stripe 的页面上再确认一次。
  • 内容不是命令。连上的邮件、文档、网页里可能夹带指令，也就是提示注入，一律当资料处理，不执行。这一点也要在授权页上告诉用户。
  • 一次连接，处处可用。连接是账号级的，网页、手机、桌面和后台定时任务共用同一份授权。后台任务没人在场，“先问”的工具不能自动放行，要推送审批、等人批准后再做。
  • 在公司里，这一步可以交给公司。用企业托管授权，员工不用逐个点同意，权限由身份系统按部门和角色统一管，离职时一键收回。

问题五

在自己的 agent 上搭一套

提问

我需要一个整体的方案，同时把现在存量的 MCP 转换过来。把我们聊的落到一个 agent 产品上，比如我个人的 personal agent，怎么实现？

分析思路

  1. 把前四问的结论落成模块、数据和流程
  2. 盘点常见客户端的 MCP 配置格式
  3. 按“在哪运行、怎么认证”给存量服务器分类
  4. 排出上线顺序和安全底线

结论

在 personal agent 的后端自建一层连接器平台：对用户只呈现“连接应用 = 授权”，对外统一走 MCP。存量 MCP 基本不用改服务器代码：导入配置，分四类迁移，再统一走三步。

完整方案另有一份文档，这里是摘要。前提是产品有云端后端，前端是网页和手机；如果只做给自己用的本地版，下面路线图的第一阶段就是全部范围。

七个模块

模块管什么关键设计

存量 MCP 怎么迁

第一步要读的配置文件：Cursor 的 ~/.cursor/mcp.json 和项目里的 .cursor/mcp.json；Claude Code 的 .mcp.json 和 ~/.claude.json；Claude Desktop 的 claude_desktop_config.json（只含本地服务器）；VS Code 的 .vscode/mcp.json。每条配置只有两种形态：url（可带 headers）是远程服务器，command + args + env 是本地服务器。注意 VS Code 的顶层键是 servers，密钥常放在 inputs 里；command 是 npx mcp-remote <地址> 的，实际是远程服务器，按地址归类。

“远程 + OAuth”这一类的旧令牌不迁移，它是发给原来那个客户端的，用户在你的产品里重新授权一次就行。常见应用的官方远程地址见问题三的表。最后，常用的组合可以按 Agent Plugins 格式打包成 plugin.json + mcp.json + skills，以后能带去别的客户端。

安全底线

上线前逐条确认。前四条不满足，就不要开放给用户：

  1. 令牌和 API key 只存在服务端保险库；前端、日志、模型上下文里都看不到原文必须
  2. 令牌绑定受众；凭据按授权服务器分开存，授权服务器变了就重新注册必须
  3. 授权码流程强制 PKCE，回调地址精确匹配，核对 iss；不用密码模式必须
  4. 工具返回的内容一律当不可信数据，不执行其中的指令必须
  5. 跨应用的数据流动，比如把邮件内容发进 Slack，一律先问：按对话记下哪些应用的数据已进入上下文，之后调用另一个应用的写入或联网工具就改为先问
  6. 工具定义变了先扣住，用户或管理员确认后才生效
  7. 网关出网走白名单，只连目录里登记的域名，拦截内网和云元数据地址
  8. 抓取 CIMD 文档、图标这类外部资源时同样设防，限制大小和超时
  9. 沙箱里的本地服务器按用户隔离，不能访问宿主的文件系统
  10. 每次工具调用写审计日志，用户看得到，并能一键断开
  11. 不做令牌透传：网关不把用户或产品的令牌转给三方服务器，也不接受不是发给自己的令牌
  12. 后台任务里“先问”的工具推送审批、排队等批准，不自动放行；批准绑定参数
  13. 写入工具超时不自动重试，防止重复发送、重复扣款
  14. 设备桥接只开放用户勾选过的本地服务器；本地服务只监听 localhost 并校验 Origin
  15. 能一键下架恶意连接器，并作废所有用户的相关令牌

上线顺序

  1. 阶段一：能连

    远程 MCP 客户端；OAuth（预注册、CIMD，DCR 只作回退）；凭据库和令牌刷新；粘贴地址添加应用；每个工具可设允许、先问、禁用；工具快照和变更扣住

    进入下一阶段：常用服务能安全调用

  2. 阶段二：好用

    目录、图标、授权摘要；工具检索和按需加载；审计日志、一键断开；请求头凭据（API key）

    进入下一阶段：新用户不看文档也能连上

  3. 阶段三：迁移

    配置导入器；沙箱托管本地服务器；桌面端设备桥接；官方注册表同步；新旧两版协议兼容

    进入下一阶段：存量配置四类都跑通

  4. 阶段四：扩展

    MCP Apps 界面；谷歌、微软原生适配；Agent Plugins 打包；多个助手和后台任务共用连接；企业托管授权（可选）

问题六

封装三方 MCP，agent loop 怎么调用

提问

实际上我可以基于现在第三方系统的 MCP，在我的 agent 产品上封装一个连接器？同时这里 harness 的 agent loop，也是通过 MCP 来调用它们？

分析思路

  1. 拆开 agent loop 的一轮：模型看到什么、输出什么、谁去执行
  2. 看接入层在调用前后各做什么
  3. 对照 Anthropic 关于工具检索的工程文章，看工具多了怎么办

结论

两个判断都对。连接器 = 三方的 MCP 服务器 + 你在外面包的一层：目录条目、授权、权限和审计。Agent loop 里，模型只决定“调哪个工具、传什么参数”；真正发出调用的，是 harness 里的 MCP 客户端，经过你的网关。

一个细节：模型本身不说 MCP

模型 API 有自己的工具格式。Harness 把从 MCP 服务器拿到的工具定义，翻译成这种格式交给模型；模型输出的调用，再翻译回 MCP 的 tools/call。所以连接器和模型是解耦的：换一个模型，不用重做连接器。

封装时你加的那一层

  • 命名空间。用“安装别名__工具”的形式命名，比如 notion__search、github_work__create_issue：两个服务器的同名工具不会撞车，同一应用连了两个账号也分得开。名字要清洗成模型 API 允许的字符，长度控制在 64 个以内，并留一张映射表。
  • 工具快照。存下每个工具的名称、说明和参数的哈希；服务器改了，先扣住，确认后才生效。工具说明会直接进模型的上下文，被人改坏了，本身就是一种注入。
  • 默认权限。由注解推导，用户可以改（见问题四）。
  • 按需加载。连的应用一多，几百个工具的说明会挤满上下文。Anthropic 的做法是先给模型一个“工具检索”，用到哪个再加载哪个。
  • 稳定性。超时、结果大小上限；只对只读或幂等的工具自动重试，写入工具超时后结果按“未知”处理，不重发。令牌过期由网关自动刷新（同一凭据串行刷新，防止被当成重放），刷新失败才打扰用户。
  • 交互界面。工具可以返回 MCP Apps 界面，在沙箱 iframe 里显示，比如一张能直接操作的表格或图表。
  • 审计。每次调用记一笔：谁、哪个助手、什么时候、调了什么、结果如何。

问题七

为什么 Tag 推连接器和插件

提问

为什么 Anthropic 在 Claude Tag 上不推 skills，而是选择连接器和插件？从 Claude 的角度，以及行业里的 agent（比如 Meta Muse、OpenAI dots）整体看看，分析一下方向思路。

追问

你从 Anthropic、Claude 的角度怎么看这个问题？深入一点。

分析思路

  1. 读 Claude Tag 的定制文档，发现问题的前提需要修正
  2. 对比 Meta Muse、OpenAI dots、Grok Bot 怎么扩展能力
  3. 读 MCP 的 Skills 扩展规范，看它怎么定位 skill 的风险
  4. 查 Agent Skills 标准和插件打包标准的来历
  5. 对照我自己作为 agent 的工作方式，标出哪些是推断

结论

Tag 也用 skill，只是把它装进插件，和连接器一起放在“能做什么”这一层，由管理员把关。在一个大家共用的 agent 里，谁能给它加 skill，谁就能改变所有人用的 agent，所以 skill 也是一种权力。推断

先修正一个前提

在 Claude Tag 里，skill 有两条来路：装在插件里（一个插件可以打包一到多个 skill），或者放进 skills 仓库，由管理员按频道下发。频道成员默认也能给自己的频道加插件，管理员可以关掉这个权限；管理员加的插件，成员删不掉。成员能直接调整的是频道指令和频道记忆，跟 Claude 说一句就记下。

三种东西，各管一件事

为什么这样设计

  • 一个共享身份，治理优先。频道里只有一个大家共用的 Claude，它用组织开通的服务账号干活。管理员最先要回答的是“它能碰什么”，这正是连接器和插件管的事。
  • Skill 本身是一个风险面。MCP 的 Skills 扩展规范要求把服务器下发的 skill 当作不可信内容，并认为它比远程调用工具风险更高：skill 想在本机执行代码，必须逐个经用户批准；它声明要用的工具权限，默认不生效。放进共享频道，一个有问题的 skill 影响的是整个团队。
  • Skill 离开工具就没用。同一份规范写明，它要解决的问题之一，就是应用服务和教 agent 用它的 skill 分开安装，用户装了服务，都不知道还有配套的 skill。插件把“钥匙”和“说明书”绑在了一起。应用方也在这么做：Stripe 推荐用它的 agent 插件，一次装好 MCP 服务器和配套的 skills，并自动保持更新。
  • 团队惯例用记忆就够了。“报告用表格”“这个线程别插话”这类要求，说一句就存进频道记忆，不需要谁去写一份 skill 文件。

行业里的几家

产品用户装的是什么skill 从哪来
Claude Tag连接器和插件，由管理员按频道配置装在插件里或放进 skills 仓库；团队惯例存进频道记忆
Meta Muse内置连接器，由 Meta 和服务商一起做每个内置连接器自带 Meta 写的 skill；它为新服务自建的集成也存成 skill
OpenAI dots插件生态里的 4,000 多个应用打包在插件里
Grok Bot“连接应用”，账号下所有 Bot 共用做过或演示过的任务存下来复用

共同点是，用户和管理员装的都是“连接”和“插件”。Skill 要么跟着连接器、插件一起来，要么由 agent 自己沉淀出来。

能力在往模型里走，缺的是访问和语境 推断

模型越强，“怎么写需求文档、怎么做代码评审”这类通用 skill 的价值就越低；真正缺的是访问权和组织语境。Tag 把语境放到了各自最合适的地方：代码仓库的安装说明写在仓库自己的 CLAUDE.md 里，由维护者更新；团队惯例进频道记忆；组织流程放进 skills 仓库。

Skill 成了基础设施，竞争在打包层

Anthropic 在 2025 年 12 月 18 日把 Agent Skills 作为开放标准发布，微软、OpenAI、Atlassian、Figma、Cursor、GitHub 都已采用，和 MCP 走的是同一条路。让应用服务通过 MCP 下发 skill 的扩展也已经定稿，Claude Code 在 Anthropic 内部做了原型。

还在竞争的是打包这一层。Agent Plugins 1.0 在 2026 年 8 月 6 日发布，由 Vercel 发起，OpenAI、AWS、Cursor、微软（GitHub、VS Code）等参与，公开的发布名单里没有 Anthropic；OpenAI 的插件文档里还有一篇教人把 Claude Code 插件提交到它的目录。Anthropic 在 Tag 里推插件，也是在经营自己的分发渠道。推断

方向判断

  • 三种角色已经分清。连接器给访问权，skill 教方法，插件打包成一次安装。Claude 的官方文档就是这么划分的。
  • Skill 跟着产品走。应用服务可以通过同一条连接下发自己的 skill，相当于“说明书随产品一起寄”。
  • Skill 越来越由 agent 自己写。Muse 把自建的集成存成 skill，Grok Bot 把做过的任务存下来复用，Claude Tag 把团队惯例存进记忆。人负责授权，agent 负责积累方法。
  • 竞争点在变。推断比拼的重点会从“有多少 skill”，转向连接器生态、治理能力，以及 agent 自己的学习能力。

Claude 的视角

这次整理时，我要读取前面写的那份方案文档。我先加载了文档系统的 skill，它告诉我那套系统该怎么用；真正读到文档内容，靠的是一组 MCP 工具。说明书教我怎么做，但给不了我任何访问权限。这就是两者在共享场景里要分开管的原因。

要带走的几个判断

  • 底层是 MCP。应用方做一次服务器，agent 方做一次接入层；接一个标准应用，基本只是填配置。
  • 仍要逐家处理的是四件事。客户端身份、目录审核、功能差异、巨头生态。
  • 官方注册表是上游的“黄页”。只存元数据、不做背书；用户看到的是各家产品目录。
  • 优先 OAuth。密码只交给应用自己；key 留给共用和无人值守；用户名密码只用于自定义连接。
  • 连接一个应用就是一次授权。背后有五个开关；令牌永远不进浏览器和模型。
  • 存量 MCP 基本不用改代码。分四类迁移，再统一走三步。
  • 连接器给访问权，skill 教方法，插件打包。在共享 agent 里，三者都由管理员把关。
